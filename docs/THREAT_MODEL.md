# Threat model

Assets: notification/media/privacy content, agent approval decisions (Phase 4), credentials, paired-client secrets, settings.
Adversaries: malicious local process, spoofed approval request, prompt-injected agent output, another Windows user on a shared machine, supply-chain tampering, curious app on the same user account.

| Threat | Control (status) |
|---|---|
| Malicious local process talks to Notch | Named pipe `\\.\pipe\com.irumva.notch.v1` with a DACL granting only SYSTEM + the current user's SID (SDDL built from the live token SID). Unauthenticated frames limited to pairing + bounded size (64 KB); everything else needs HMAC-SHA256 with a per-client secret, 60s timestamp window, single-use nonces (1024-entry replay cache). Fail-closed if the SID cannot be read (server does not start). Implemented + Rust unit tests; live E2E verified in Phase 3. |
| Spoofed / replayed approval requests | Phase 4 builds on the same envelope: approvals bind request ID + hash of the exact action, expire, single-use (brief section 3C). Phase 3 supplies pairing, HMAC, replay guard (`src/security/ipcProtocol.ts`, `src-tauri/src/security.rs`). |
| Prompt injection via agent/tool output | All external text renders as inert React text nodes; no `dangerouslySetInnerHTML`, no markdown/HTML link activation anywhere. IPC payloads are length- and charset-validated twice (Rust server, then `validateIpcPayload`). |
| Notification/media content leaks on a locked or shared screen | Activities can be flagged `sensitive`; `redactForLock` replaces title/subtitle/data with "Private activity". Workstation lock detected via `WTSRegisterSessionNotification` on a hidden message window (`notch://session-lock`), plus a manual lock toggle in Security settings. Notification *contents* are never persisted (Phase 2 provider is disabled anyway, A7). |
| Another Windows user reads Notch data | Settings and paired-client secrets are DPAPI-encrypted (current-user scope) in `%APPDATA%\com.irumva.notch`; secrets live only in Credential Manager (`Notch by IRUMVA:<key>`). Pipe ACL excludes other users. |
| Credential theft from settings files | `SecureSettings.save` refuses keys matching secret/token/password/api-key patterns; secrets must go through Credential Manager APIs. Export never includes secrets (`data_export` states this in its output). |
| Supply chain / update tampering | Dependencies pinned by lockfiles (`package-lock.json`, `Cargo.lock`); SBOM generated by `scripts/sbom.mjs`; signed updater + Authenticode are Phase 6 (no cert yet, ASSUMPTIONS A5). |
| Plugin abuse (Phase 7) | Not in scope yet; the pipe's client model (paired secret, schema-validated activities, priority clamped 0–100) is the boundary plugins will inherit. Deny-by-default. |
| Denial of service via the pipe | 64 KB frame cap (connection dropped), one handler thread per connection, max 4 pipe instances, provider event bus bounded (Phase 1). Pairing locks after 5 bad codes; codes expire in 5 minutes and are single-use. |

## Verification in Phase 3
- TS tests: HMAC round-trip + tamper/wrong-secret rejection, replay + stale-timestamp rejection, lock redaction, settings secret-refusal, IPC payload validation (`app/src/security/security.test.ts`).
- Rust tests: canonical-JSON equivalence with the TS implementation, HMAC tamper detection (`cargo test`).
- Live E2E: Node client pairs with a one-time code from the Security panel, sends signed `ping` and `activity.publish`, island displays the activity; unsigned and replayed frames are rejected.
- Residual: same-user malware can already read the screen/keyboard; the pipe defends against *unauthenticated* and *other-user* processes, which is the documented boundary. Windows Hello gating for high-risk approvals is wired (`hello_verify`) and exercised in Phase 4 approval cards.
